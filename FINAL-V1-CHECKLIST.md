# Final Service-Sait V1.0! — інструкція встановлення, тестування й запуску

**Статус: реліз-кандидат.** Код у гілці release/final-service-sait-v1.0 не означає, що він перевірений з вашою локальною PostgreSQL або доступний покупцям. До завершення цієї інструкції НЕ об'єднуйте його з main.

Репозиторій: https://github.com/stas1212212/Servis-Sait
PR: https://github.com/stas1212212/Servis-Sait/pull/16

## 1. Завантаження на Windows

У PowerShell у папці E:\server\Servis-Sait:

    git status
    git fetch origin
    git switch release/final-service-sait-v1.0
    git pull --ff-only origin release/final-service-sait-v1.0
    npm ci
    npm run check:js
    npm test

Якщо git status показує незбережені зміни — спершу збережіть їх в окремому коміті чи backup. Гілка вже містить попередні PR: не копіюйте вручну файли зі старих гілок поверх неї.

## 2. Обов'язково зробіть backup PostgreSQL

1. Відкрийте pgAdmin → Databases → service_shop → Backup, формат Custom, збережіть .backup.
2. Переконайтеся, що backup не порожній.
3. Створіть окрему тестову БД service_shop_staging та відновіть туди backup.
4. Перші міграції та тестові замовлення виконуйте в ТЕСТОВІЙ БД, не на бойових даних.
5. Увага: НЕ запускайте знову server/sql/import-existing-products.sql на робочій БД — імпорт через ON CONFLICT UPDATE може перезаписати ціни й реальні залишки товарів.
6. Стара database.sql — неповна схема, НЕ пересоздавайте з неї наявну БД.

## 3. SQL-міграції (тільки після backup)

Наведена послідовність залежностей. Запускайте в pgAdmin Query Tool на тестовій базі, якщо відповідну міграцію ще не застосовано:

1. Базові users, products, orders, order_items, service_requests мають уже існувати.
2. server/sql/admin-setup.sql — роль admin.
3. server/sql/customer-service-suite.sql — відстеження, сповіщення, сайт, відгуки.
4. server/sql/shipping-setup.sql — відправлення й приймання ремонту.
5. server/sql/store-catalog-setup.sql — категорії / бренди магазину.
6. server/sql/order-history-visibility.sql — приховування замовлення тільки в кабінеті.
7. server/sql/carrier-choice-map.sql — Нова пошта / Укрпошта і карта.
8. server/sql/final-v1-setup.sql — ОБОВ'ЯЗКОВА для релізу: контакти покупців, ID товарів, контроль складу, історія статусів, постійні сесії та захист входу.

Якщо раніше був застосований order-tracking-setup.sql, фінальна міграція використовує безпечні IF NOT EXISTS для його суттєвих елементів. Вона не має видаляти старі заявки, клієнтів або замовлення. Старі order_items без product_id НЕ можна автоматично прив'язувати до товарів за назвою: потрібна ручна звірка, перш ніж повернути їх на склад.

Після успіху на staging зробіть НОВИЙ backup бойової service_shop, а тоді окремо застосуйте необхідні міграції до неї.

## 4. Конфігурація сервера

Використайте server/.env.example як зразок, але не публікуйте жодного реального пароля чи .env у GitHub. Для тестів зазначте DB_NAME=service_shop_staging, справжні DB_HOST, DB_USER, DB_PASSWORD, DB_PORT.

SESSION_SECRET — щонайменше 32 непередбачувані символи. Для production: NODE_ENV=production і PUBLIC_BASE_URL=https://ваш-домен. TRUST_PROXY=1 — лише за довіреного реверс-проксі з HTTPS.

Для листів скидання пароля необхідні RESEND_API_KEY, перевірений MAIL_FROM та правильний PUBLIC_BASE_URL. Без них відновлення через email не працюватиме.

    node --env-file=server/.env scripts/release-preflight.js
    node --env-file=server/.env server/app.js

Скрипт preflight нічого не змінює в БД. [BLOCK] = необхідна дія перед публікацією; [CHECK] = перевірити вручну. Після старту відкрийте http://localhost:3000.

## 5. Реальні бізнес-дані

- На /admin-hub.html заповніть дійсні: телефон, email, Telegram, адресу, години роботи, юридичну назву / ПІБ ФОП, реєстраційні відомості.
- Перевірте /contacts.html, /privacy.html, /delivery.html, /faq.html, футер. Не залишайте «Уточнюється» у важливих даних.
- На /admin-shipping.html ОКРЕМО задайте для Нової пошти та Укрпошти ПІБ фізичної особи-одержувача, телефон, місто, номер відділення, повну адресу, точні координати Google Maps. Не ставте приблизну мітку міста.
- Додайте тільки реальні товари, актуальні ціни, склад, сумісність, назви й фотографії. Активні товари без фото або з вигаданою ціною — НЕ до публікації.
- Узгодьте умови діагностики, гарантії, повернення, оплати, документи та фіскалізацію з бухгалтером/юристом. PULT+ v1.0 НЕ стягує оплату банківською карткою; умови погоджує менеджер.

## 6. Чекліст ручного тестування

### Акаунти й права

- [ ] Реєстрація нового покупця, пароль 10+ символів; відхилення дублікату email.
- [ ] Вхід/вихід/повторний вхід, помилки на невірний пароль.
- [ ] Після перезапуску Node сесія збереглася в PostgreSQL до закінчення терміну.
- [ ] Якщо налаштовано email: запит, лист, скидання пароля, прострочене посилання.
- [ ] Звичайний клієнт не бачить кнопку адмінки і не відкриває /admin.html, /admin-hub.html, /admin-shipping.html напряму.
- [ ] Адмін бачить кнопку; звичайний покупець не бачить чужі замовлення, ремонти чи приватні реквізити одержувача.

### Магазин і склад

- [ ] Відкривається каталог; працюють категорії, бренди, пошук, сторінка товару, фото й правильні залишки.
- [ ] У кошику кілька різних категорій, кількість змінюється, видалення і загальна сума правильні.
- [ ] Порожній кошик не оформлюється.
- [ ] Checkout зберігає справжні ім'я, телефон, email, перевізника, місто, відділення, коментар.
- [ ] Адмін бачить саме ЦІ контакти і відділення, а не тільки email акаунта.
- [ ] Після покупки видно номер на thanks.html, у кабінеті видно історію.
- [ ] Після покупки складський залишок зменшується лише один раз; повтор того самого checkout не створює дубля.
- [ ] Скасування нового замовлення повертає складський залишок рівно раз; у статусі є історія.
- [ ] Відправлене замовлення не можна просто скасувати зі штучним поверненням на склад.
- [ ] Старе замовлення без product_id не скасовується автоматично: повідомлення про ручну звірку.
- [ ] «Прибрати з історії» в кабінеті не означає скасувати замовлення в адміністратора.
- [ ] Два одночасні замовлення останньої одиниці товару не роблять залишок від'ємним.

### Ремонт і доставка

- [ ] Надіслати тестову заявку для всіх форм техніки, отримати RP-код і сторінку repair-submitted.html.
- [ ] RP-код збігається в підтвердженні, кабінеті й адмінці; різні заявки отримують різні RP-коди.
- [ ] Клієнт обирає Нову пошту або Укрпошту; адреса й Google Maps належать саме потрібному відділенню.
- [ ] До підтвердження менеджером приватні ПІБ і телефон одержувача НЕ видно.
- [ ] Після підтвердження дані бачить власник заявки чи гість із ключем тільки у своїй вкладці.
- [ ] Працюють номер Нової пошти з 14 цифр і трек-номер Укрпошти з 13 символів.
- [ ] Менеджер фіксує зовнішній стан, комплектацію та серійний номер пристрою при отриманні.
- [ ] Працюють статуси ремонту, відстеження RP, повернення пристрою й модерація відгуку завершеного ремонту.

### Дизайн і безпека

- [ ] ПК і телефон: усі важливі сторінки в світлій та темній темі (магазин, товар, кошик, checkout, кабінет, адмінка, ремонт, доставка).
- [ ] Українська / російська / англійська мови: немає технічних SQL-повідомлень для клієнтів.
- [ ] Посилання, кнопки, введення, доступність з клавіатури, читабельність помилок.
- [ ] Запити до приватних API без входу відхиляються; звичайний користувач не може редагувати товари й замовлення.
- [ ] У браузері перевірені HTTPS, secure cookies, робота сесій, відновлення з backup та журнал помилок.
- [ ] Усі рекламі заяви на сайті мають правдиве підтвердження.

## 7. Що залишається за адміністратором при публікації

1. Оренда хостингу з Node.js 22+, PostgreSQL, постійним сховищем і регулярними backup.
2. Придбання домену, DNS, HTTPS/TLS, правильний проксі й environment secrets.
3. Перевірка продакшн-збірки CSS: в окремих сторінках залишається браузерний Tailwind CDN; для надійного production його потрібно замінити на локально зібраний CSS і знову пройти візуальні тести.
4. Перевірка умов продажу, оплати, гарантії, документів і законності роботи.
5. Моніторинг, повідомлення про помилки, тест реального відновлення backup, план відкоту.

**Критерій запуску:** npm test / npm run check:js успішні; preflight не показує [BLOCK]; усі критичні пункти перевірені на справжній staging PostgreSQL; на публічному HTTPS працює повний цикл покупця й ремонту. Лише тоді можна об'єднати релізну гілку з main і приймати клієнтів.
